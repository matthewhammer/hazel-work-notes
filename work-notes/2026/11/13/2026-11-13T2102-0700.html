What they agreed

Matthew's summary, given on 11-15 at 11:3x, all about hazel-jit:

we want semantic consistency with Hazel the interpreter, and to ensure that with CI, and our design decisions.

priotities:

arb precision Ints and Nats --- we want to use bignum in the output if we can, or something comparable, not native JS numbers for Ints and Nats.

when we hit an overflow for any times where that is possible -- we should check each time for non-arb precision numbers --- we should create an indet term / stuck term with that error -- look at existing interpreter cases for inspiration.

similar for divide by zero

for the output of hazel-jit, we should continue to avoid translating code with holes, and we should exclude "stepper functions"

probes, step budgets, and all other limitations we should work to overcome in the coming days.

So hazel-jit changes course, from "the best case of how much faster JS could run some Hazel code", where numbers could differ from Hazel's, to code that means what the interpreter means, checked in CI. The interpreter's Int and Nat are arbitrary precision (Bigint), and its bad operations stop at stuck terms with errors (DivideByZero, IntegerTooBig, ...). Today hazel-jit makes every number a JS number and lets Infinity and NaN through. The "stepper functions" are the stepper's filters, hide, eval, pause and debug P in e, which say which steps the stepper shows; hazel-jit already leaves them, and holes, to the interpreter.

A major concern of Cyrus's: a step limit

another major concern from Cyrus, from meeting on 11-13:

We need a way to limit compiled hazel functions that diverge --- we need a step limit.

esp if we continue to optimize by including certain jit-compiled hazel functions into the main thread

Matthew, on 11-15 at 11:4x. The interpreter counts its steps and stops a run that goes on too long; compiled code has no such limit, so a function that never ends would loop forever. And some compiled code already runs on the page's main thread: since ^ticket(722), at a livelit's event, the slide's compiled run draws the livelits before the worker's run comes back. A diverging function there would freeze the page, so the limit comes before any more of that.
