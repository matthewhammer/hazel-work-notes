In short

  • The review's main point holds: two separate URL encodings (the scratchpad's ?name=&share= and this PR's ?slide=), parsing tangled with applying, and nothing testable without a browser.
  • The plan: one type for a whole deep-link request, parsed from the query (passed in) apart from applying it, so parsing, the editor actions and making the URL can each be tested; applied as an action from Main.re; slide_name off Globals; the panel names in one switch in Sidebar.re; and the small fixes below.
  • Open questions for Matthew: whether the scratchpad's share encoding moves into the same type in this PR or a follow-up; the copied span (selection or caret, instead of the enclosing term); tutorials (not in this PR).

One request type, parsing apart from applying

Following the existing panel_request pattern, as the review suggests. A sketch, not settled code:

type target =
  | Slide(string)                   /* ?slide=   a documentation slide, by name: a pointer */
  | Share(string, string);          /* ?name=&share=   a scratchpad's contents: a snapshot */

type position =
  | Caret(Point.t)                  /* ?caret=  */
  | Select(Point.t, Point.t);       /* ?select= */

type request = {
  target: option(target),
  panel: option(panel_request),     /* ?panel=  */
  position: option(position),
};

let parse: (string => option(string)) => request;      /* the query lookup passed in */
let to_params: request => list((string, string));      /* parse(lookup(to_params(r))) == r */
let settings: (request, Settings.Model.t) => Settings.Model.t;
let action: request => option(Action.t);

Tests, without a browser: parsing each parameter and its edge cases (empty values, a column past the line's end, a range of whole lines, junk); the round trip from a request to a URL and back; the loose matching of a slide name against a list of names; and the action a request makes.
