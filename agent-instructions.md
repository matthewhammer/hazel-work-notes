# Hazel Work Dashboard: agent instructions

The Hazel Work Dashboard is how Matthew and his agent keep track of Hazel work, across sessions, machines and time: what is served where, which PRs are open and how they stand, and what to do next. It is one page, http://localhost:8000/, and this repository is its history.

Read this before working with Matthew on Hazel. Keep the dashboard current as you go: it is the shared memory between sessions.

**This repository is public, and so is the dashboard** (since 2026-10-13, Matthew's call): a copy of the page is published at https://matthewhammer.org/hazel/dashboard/ (since 2026-10-16, ^ticket(181); its earlier addresses, http://matthewhammer.org/hazel-work-notes/ and http://matthewhammer.org/hazel/work-dashboard/, redirect there, `#ticket-N` and all), so Matthew can see where things stand away from the laptop. Link tickets there: `https://matthewhammer.org/hazel/dashboard/#ticket-N`, or `closed.html#ticket-N` once closed. Nothing in it is secret, but nothing secret may go into it either: no tokens, keys or passwords, and Matthew's kids only as M and N.

**This repository is our working record, for the two of us:** what is served where, how the PRs stand, what to do next, and the dashboard's history. It is written in shorthand, for people who were there.

**The Hazel reports series (until 2026-10-19 "Hazel performance analysis"; its old addresses forward) is separate,** in its own repository, [`hazel-performance-analysis`](https://github.com/matthewhammer/hazel-performance-analysis), with its own agent instructions. It is written for readers outside the loop: Cyrus, the Hazel team and others. The dashboard links to the series (`^report(7)`), but working notes never go into a report. When work here answers a question worth sharing, that answer becomes a report there.

## Tickets: our own numbers

We call them **tickets**, not issues: an issue is a GitHub issue, and the performance analysis series is made of **reports**. **Write a ticket as `^ticket(N)` and a report as `^report(N)`** (Matthew's syntax, 2026-10-14): in `data.json`, on the page and in chat; no leading zeros, so numbers can grow into the thousands without passing for a PR. The page shows both in monospace, with `^ticket(` / `^report(` and `)` in bold, each a link.

- Each ticket has a number, `^ticket(N)`, from `data.json`'s `next_ticket`. **A number is never reused.** Take `next_ticket` for a new ticket, then increment it.
- **When Matthew calls something important and it is not started, open a ticket right away,** in `tickets`, with an area, its text, where it came from (`source`, and a `url` when there is a real one) and the date (`added`).
- **The current ticket** is the one we are working on now: `current_ticket` is its number, `current_since` when we started it, and `current_note` says in a line what is next on it. The page shows it first, with the start time and the time elapsed since, in Matthew's local time (Mountain Time, Colorado). Set it when Matthew starts one ("let's do #N", or a pasted ticket link), with `current_since` the time of his message; keep the note up to date as the work moves; set it to `null` when no ticket is in hand. Only an open ticket can be current. **When the work waits on Matthew** (a draft to look at, a publish or a push to approve), say so in the note at once, with where it is (a commit, a local URL) and what he needs to decide; the edit to `data.json` is published within a minute. He reads the published copy from other computers to know when he is the one holding things up, and comes back to the session to answer. Reword it once he has. Set `current_waiting` too, to `true` or a short line saying what he needs to decide: the page then shows ✋❔ in a bold box next to the current ticket's heading, on its row and in the outline, and at the front of the page's title, so a browser tab shows it unopened. Remove it (or set it to `false`) as soon as he answers: **in the same turn as his answer, before any other work** (Matthew, 2026-10-18, after ✋❔ stayed up on the page while he had already answered: "your hand is still 'up' on localhost:8000 ... please be accurate"). Any reply of his to the question counts as an answer, even one that reports a new problem; reword `current_note` to what is being done with it. The published copy lags: `site_publish.py` puts it up at most every ten minutes, the homepage's build takes about two, and GitHub Pages lets a browser keep a copy ten minutes more (`max-age=600`); so when he asks whether ✋❔ is still up, read the published HTML with a cache-buster (`?t=…`), say when it last went up (its `last-modified`), and tell him Ctrl+Shift+R if his copy is older.
- **The work queue** (`queue`, ticket numbers, front first) is the short list of what we mean to do next, in order: a few tickets, not the backlog. The page shows it right after the current ticket, as **Work Queue (Active Tickets)**, each ticket a line linking to its row; every open ticket is in **Full Backlog (All Tickets)** below, a queued one with a "queued" chip, the status beside "current" (one ticket at a time is current; the others in the queue are queued). Matthew pushes a ticket onto the front or the back ("push #N to the front", "put #N after #M", "move #N up"), or reorders it; edit `queue` in the same turn. **"Mint and enqueue"** means: push it to the end of the active queue, the non-blocked tickets, so before the 🌙 long runs and the 🪷 blocked ones. The queue is then worked in its order, the order the tickets came (Matthew, 2026-10-17: "no need to reorder the queue -- we have a lot, and can do them in order that they came"); don't offer to move a new ticket up. When a ticket in the queue closes, take it out of the queue in the same edit. When the queue's front ticket is started, it becomes the current ticket and stays at the front until it closes. A number in `queue` that is not an open ticket is left out of the page, and update.py says so.
- **🌙 Long runs** (Matthew's, 2026-10-15): a ticket he tags "long run" (`"tags": ["long run"]`) is work to do while he is away from the keyboard: renders, archives, big sweeps, anything long that needs no suggestions from him or the kids. Keep long runs together at the end of the queue (the page puts them under a "Long runs" line once they are all at the end), take them when he says he is stepping away or "tonight", and still run heavy jobs one at a time (the laptop crashes under load). When he calls something "for tonight", tag it and move it there.
- **🪷 Blocked on Matthew** (Matthew's, 2026-10-15): a ticket tagged "blocked on Matthew" waits for his response (a reply he writes by hand, a decision only he can make). Keep these in their own category at the very end of the queue, after the long runs; untag it and move it back up the moment he answers. This is for tickets that are not current; the current ticket's wait is still `current_waiting` (✋❔).
- **Closing a ticket moves it** from `tickets` to `closed_tickets`, never deletes it. Keep its `text` as it last read, and add:
  - `closed`: the date;
  - `status`: **done**; **not needed** (its premise turned out wrong, or there was nothing to do); **dropped** (we decided not to, and why); or **superseded** (another ticket took it over: name it);
  - `outcome`: what came of it, with its commits, PRs, reports of the series or other tickets; and `outcome_url` when one page holds it.
  If it was the current ticket, choose the next current one, or `null`.
- **Every ticket keeps its own metrics** (Matthew, 2026-10-15), so that estimates can be checked against what things really took:
  - `opened`: when it was minted, and `closed_at`: when it was closed, each ISO 8601 with its offset and to the minute (`2026-10-15T10:05-06:00`), from `datetime.now().astimezone()`, never a bare date. `added` and `closed` stay the dates they were.
  - `log`: one entry per message about the ticket: `{"at": <ISO time>, "from": "matthew" | "claude", "chars": <its length>, "asks": true | false}`. `chars` is the message's length (for a reply that is mostly tool output, only the text he reads); `asks` is true when a message of Claude's puts a question to Matthew that needs his answer before the work can go on (an offer he may ignore is not one). **Since 2026-10-20 the entries come from the session transcripts** (`dashboard/log_messages.py`, run by `publish.py` every five minutes, ^ticket(466)): kept by hand they were not kept, and 100 closed tickets said Matthew had sent nothing, the horse and the outfits among them. It places each message by, in order: the tickets it names; the tickets whose text or progress quotes it (so **quote his words in the ticket**: that is what ties a message to its ticket); the tickets minted in the 20 minutes after a "mint"; a follow-up within 10 minutes goes where the message before it went; else the current ticket (so **keep `now.py` current**). An entry written by hand still counts, and places the transcript's message nearest it (3 minutes) on its ticket, with the exact time and length; write one, in the schema above, only when the rules would get a message wrong. `python3 log_messages.py --backfill --since <date>` rebuilds every log from that date (it was run from 2026-10-15); `--dry-run` shows what it would do.
  - Since 2026-10-20 (^ticket(489), Matthew: "log how long the average reading time is for each thing you print, and assume that I am reading or listening to it"), a Claude entry also has `words` (the words of the text he sees), `read_s` and `listen_s`: the seconds to read it at 238 words a minute (silent reading of non-fiction, Brysbaert 2019) and to hear it at 160 (speech and narration, 150-160). The rates are `READ_WPM` and `LISTEN_WPM` in `dashboard/log_messages.py`. A ticket's `metrics` add `replies`, `claude_words`, `read_minutes_est`, `listen_minutes_est`, `read_s_avg` and `listen_s_avg` when its entries have words (tickets logged before 2026-10-15 have none). data.json's `reading` is the all-time tally ("for all time", his words): every reply in every session transcript, by day (`days`: replies, words, chars), with the totals, averages and rates; log_messages.py reads each transcript on from where it stopped, a minute at most per run, and the page shows it under its opening notes.
  - On closing, `metrics`, computed from the log: `open_minutes` (opened to closed); `matthew_messages` (his entries); `questions_to_matthew` (Claude's entries that ask); `chars_exchanged` (all entries' chars) and `tokens_est` (chars / 4); `sync_minutes_est`, the time spent together: the sum of the gaps between consecutive entries shorter than 10 minutes, so that work either of us did alone, between messages, is left out; and `work_minutes`, when the work itself was timed (as `^ticket(92)`'s hallway was), with its start and end.
  - The closed tickets' page shows the metrics under each outcome. A ticket from before 2026-10-15 has none; estimate them only if its messages can still be found.
- **A pasted ticket request mints a ticket.** Each "What next" step in the Hazel reports series has a "copy for a ticket" button; it copies `Mint a ticket for this step: Hazel performance analysis, ^report(N), What next, step N: "<title>". <URL>` (before 2026-10-14, "issue NNN"). When Matthew pastes that, open a ticket for exactly that step: its text from the step, `source` "issue NNN, What next, step N", `url` the step's URL. Ask whether it becomes the current ticket, unless he says so.
- **A parked ticket stays open,** with "PARKED", the date, and the measurement that parked it.
- Each ticket's row has the anchor `#ticket-N`, and a "copy link" button that copies http://localhost:8000/#ticket-N. Old links, `#next-N`, still work, and a link to a closed ticket takes the reader to its row on the closed page. **When Matthew pastes such a link, he means exactly that ticket:** read the ticket with that number in `data.json`, in `tickets` or `closed_tickets`. Never guess from the wording.

## Links

Write references plainly in `data.json`, and `update.py` links them the same way everywhere:

- `^report(6)` links to that report of the Hazel reports series (an older "issue 006" in a text still does). That is the public page once it is published (`~/matthewhammer.github.io/hazel/reports/006/` exists), and the local draft at http://localhost:8131/series/006/ until then.
- `#2161`, four digits or more, links to hazelgrove/hazel on GitHub, and `owner/repo#N` to that repository; every such link gets a card on hover or focus (title, state, author, dates, comments), asked of GitHub live, with what GitHub said at the last publish as the fallback (`dashboard/prlinks.py`, `pr_cards.html`; Matthew's rule, 2026-10-14).
- `^ticket(10)` links to that ticket (an older `#10`, one to three digits, still does): its row on the dashboard while it is open, and on the closed page once it is closed.
- A 10-character commit id, such as `bd90642654`, links to the commit.

Text already inside a link is left alone. Give a ticket a `url` only when it has a real source; otherwise leave `url` empty, and its "From" is plain text.

## Keeping it current

- **Update in the same turn as the change:** a server started, stopped or moved to another port; a PR opened, retitled, merged or closed; a worktree switched to another branch; a ticket opened, made current, closed or parked. Within a minute, cron sees that `data.json` changed and publishes it, so an edit to `data.json` is all it takes; to publish at once, or after a change that is not in `data.json`, run `python3 ~/localhost-index/publish.py --now`.
- At the start of a session, run `python3 ~/localhost-index/publish.py --now` once, and make sure the `localhost-index` server is up.
- **Serve what the dashboard links** (Matthew's rule, 2026-10-15, after http://localhost:8131/series/ was down for half an hour behind a live link). At a session's start, and after any crash or restart, start every server the Localhost ports table links, not just the ones the work in hand needs, and check each link answers (and, for a `dev_serve.py` server, that `/status.json` names the row's worktree and branch, with no stale sources). A link that cannot be served is marked "not served" in its row, with why, in the same turn: a dashboard link that goes nowhere is a bug. Close the browser pane's tab a Hazel server opens: the servers keep running, and the app costs this laptop a lot.
- **The 5-server limit is the Claude desktop app's** (its preview tool, `preview_start`: "Maximum 5 servers per worktree"), not the laptop's: every entry in `~/hazel/.claude/launch.json` started from a session in `~/hazel` counts against `~/hazel`. A sixth needs one stopped, a session opened in another worktree (its own five), or Matthew's go-ahead to run it in a Terminal tab instead.
- **Launch entries are named with their PR,** such as `#2635 hazel-livelits-modular` or `fumola#129 fumola-pages-wt`. Rename an entry when its worktree's branch, and so its PR, changes. The app runs at most 5 preview servers per worktree, so stopping one may be needed to start another.
- **Always tell Matthew the port, and what build it serves,** in chat. Never put local ports in a PR description: there, say "in the browser".
- **The AFK protocol** (Matthew, 2026-10-19: "keep going and signal with 'blocked on Matthew' for any ticket that needs me. let's be efficient, and asynchronous!"). While Matthew is away, never stop to wait. A ticket that needs his answer is tagged "blocked on Matthew" (with `waiting`), its question goes in its progress, and work moves to the next ticket in the queue (`now.py`). A wait on CI is not a reason to stop either: leave a background watch on it and work on something else until it reports.

## Versions

The dashboard's code has a version number, `VERSION` in `dashboard/update.py`, which the page shows in its History line. [`VERSIONS.md`](VERSIONS.md) lists the features of each version, newest first. It started at 0.0.1 on 2026-10-12.

- **When a change to the code adds or changes a feature,** bump `VERSION`, add the new version to `VERSIONS.md` with its date and what it changed, and commit the code with it. `log_notes.py` commits only snapshots, so the code is committed by hand. Since cron may be committing in this repository any minute, hold its lock while you do: `flock ~/localhost-index/.publish.lock git commit ...`, and the same for the push.
- A change to `data.json` alone (a port, a PR, a step) is content, not a new version.

## The history

`log_notes.py` writes the page and the closed page to one path each, `dashboard-snapshots/index.html` and `closed.html`, exactly as served, and commits them when they changed in more than the "Updated" line: every version is a commit, its time the commit's, and `dashboard-snapshots/versions.html` lists them from `git log` (one pass, newest first, links to each on GitHub); then it commits data.json, publishes the public copy and pushes, retrying the push on every run. Since 2026-10-19 (^ticket(417), Matthew: "no prior snapshots are kept as separate files, but only as part of the git history ... this protocol is not going to scale"): until then each version was a dated file, `dashboard-snapshots/<YYYY>/<MM>/<DD>/<YYYY-MM-DD>T<HHMM><+-hhmm>.html`, 1,830 of them and 341 MB on the laptop, ~95 MB a day (^ticket(391)); they left the tree and stay in history, all in the tree of `df072c9d` (`dashboard-snapshots/.dated-until`). To see a version: `git show <commit>:dashboard-snapshots/index.html > then.html`. Keep `.git` packed with a `git gc` now and then, holding the publish lock.

## `data.json` fields

- `ports`: rows with `pr`, `repo`, `branch`, optional `base`, and `links` as `[text, url]` pairs. A row without a PR has `name`, `repo_html`, `branch`, an optional `branch_note`, and `links`.
