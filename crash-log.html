Matthew’s work laptop (a Framework Laptop 13, 13th Gen Intel Core, BIOS 03.04, 20 CPUs). Started 2026-10-16 after the day’s third crash, from the system journal back to 2026-08-18. Kept by Claude with Matthew; a new crash gets a row at the top. Updated 2026-10-18 13:25 MDT.

What the evidence says

  • The laptop sees no battery. Every boot whose kernel log survives, back to 2026-08-18, says ACPI: battery: Slot [BAT1] (battery absent). The only power supply it lists is the adapter (ACAD, mains). The whole history below ran on the adapter alone.
  • No crash leaves a reason. There is no shutdown, panic, machine-check or thermal line: the journal just stops. Lines still in memory when the machine dies are lost, so the last line only says it was alive until then (at 16:47 on 10-16 a session was still writing at 16:47:08, seven seconds after the journal’s last line).
  • Nothing could leave a reason as set up now. The kernel is set never to panic on a hang (kernel.panic = 0, softlockup_panic = 0, hardlockup_panic = 0), and the crash-dump store (/var/lib/systemd/pstore) is empty. A hard freeze and a power cut look alike in these logs.
  • Two kinds, by Matthew’s words: “froze” (10-16 16:33 and 16:47) and “got unplugged” (10-11). With no battery, a moment without the adapter is a power cut. A freeze, a screen left still, is something else, or a dip that hangs the machine instead of cutting it off. The 08-28 crash ends on gnome-shell falling behind on the Power Button’s events, so that one was probably a freeze ended by holding the button.
  • The clock is now lost when the adapter is off. After the 10-15 15:33 crash, after the clean power-off at 10:34 on 10-16 (when Matthew moved the laptop), and after the clean power-off at 12:41 on 10-17, the hardware clock read 2023-01-01 00:00 at boot. Every earlier boot read the right time. So with the adapter out, nothing keeps even the clock going.
  • Some crashes come under load, some at idle. Under load: 09-22 (a build, the test suite and WebDriver, stacked), 09-28 12:48 (two sessions building), 10-16 16:33 and 16:47 (headless Chromium running Dress Up’s speed tests), 10-16 20:47 and 20:53 (headless Firefox, pinned, the same run twice), 10-19 10:26 (a dune build linking with js_of_ocaml, seconds after another build). At idle: 09-26 (twice), 09-29 16:05, 10-16 08:01, 10-17 15:42, 10-18 08:11, 10-18 10:40 and 10-18 13:16, all with a load under 3 on 20 CPUs where a reading survives (0.16 at 08:11 on 10-18; at 10:40 and again at 13:16 the app’s browser pane had the game open and a release had just been pushed; no reading survives for 13:16).

A reading that fits all of it, not proven: a laptop with a battery rides through a burst of power above what its adapter gives, and through a dip in the adapter, cable or USB-C power negotiation. This one has nothing to draw on, so either one stops it, at idle or under load. What would test it: a battery it can see (or, if one is fitted, its connector reseated), or a stronger USB-C adapter and cable; then see whether the crashes stop. Until then the rule stands: one heavy job at a time, and commit and push early.

In use since 2026-10-16 17:05 (Matthew’s call, after the 16:47 freeze): headless Chrome and the tools that drive it are pinned to 4 of the 20 threads (taskset -c 0-3 nice -n 10), to cap a burst of power. By 18:10 it had run the fps gate five times, 🧪, the still-picture, door, collision and pit checks, and the day’s 586-picture archive, about an hour of browser work, with no crash; the gate read the same as unpinned (10 of 10 at 59.3 to 60). Not proof that it helps: the 16:46 trial and the 16:40 gate ran unpinned without a crash too. It did not prevent the 20:47 freeze, about 90 seconds into a pinned headless-Firefox run (the same 4 threads, nice -n 10); the run before it read the CPU package at 58 to 72 °C. Nor the 20:53 one, about 45 seconds into the same run started again. All four crashes of the evening came while a headless browser ran.

From 2026-10-16 20:56, Matthew’s ask: no headless browser (Chromium or Firefox) runs on this laptop, pinned or not, and one heavy job at a time across all sessions.

Worth noting next time

  • Did the screen stay lit and still (a freeze), or go dark at once (a power cut)? Did the keyboard’s lights or the fan still respond?
  • Was the adapter touched, moved, or plugged into something else?
  • A way for a freeze to leave a record (Matthew’s to do, as it changes system settings): set kernel.softlockup_panic=1, kernel.hardlockup_panic=1 and kernel.panic=10, so a hang becomes a panic that reboots after 10 seconds; the panic’s text then lands in /var/lib/systemd/pstore (EFI pstore) for the next boot to read. A power cut would still leave nothing, which tells the two apart.

Adding a crash

After a crash, and before starting anything heavy:

journalctl --list-boots                          # the boot before this one: its LAST ENTRY is the crash
journalctl -b <boot id> -n 30 -o short-iso        # a clean end has systemd-shutdown or "Journal stopped"
journalctl -b 0 -k -g 'RTC time|BAT1'            # the clock at this boot, and the battery
LC_ALL=C sar -q -f /var/log/sysstat/saDD -s HH:MM:00 -e HH:MM:00   # load before it
  • Use boot ids, not offsets like -b -1: a boot that starts with the clock reset sorts out of order and the offsets point at the wrong boots.
  • What was running: the Claude transcripts last written before the crash, and Matthew’s word for it (froze, went dark, unplugged).
  • What was lost: look for zero-length files written in the last minute before the crash, and move them aside before rerunning anything that keeps existing files.
  • Look for empty git objects in every repository (find ~/*/.git/objects -type f -empty), even ones whose work was pushed (10-17 15:42). Move them aside, then bring the objects back from GitHub: a bare clone with its pack copied into .git/objects/pack/, or, for a big repository, set the remote branch back to its last good reflog entry and fetch. Then run git fsck, and strip any NULs from the reflogs in .git/logs/.
